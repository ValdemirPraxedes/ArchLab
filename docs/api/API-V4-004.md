# API-V4-004 — Política de adaptação de payloads legados

**Decisão para BE-V4-01.** Escopo: preservar clientes v1/v2 durante a migração para o contrato canônico v0.4 de `docs/api/openapi.yaml`. Esta política especifica a futura implementação; nenhum adaptador Java foi criado nesta etapa.

## Identificação do formato

| Rota e corpo | Interpretação | Ação |
| --- | --- | --- |
| `/api/v1/architectures/validate` com `components` e `connections`, conexões com `protocol` | v1 legado | Aplicar regras v1 e adaptar apenas para representação interna; preservar `ValidationResponse` e violações legadas. |
| `/api/v1/simulations` com a mesma arquitetura direta | v1 legado | Validar primeiro pelas regras v1, depois adaptar arquitetura e derivar o único cenário permitido. |
| `/api/v1/scenarios/validate` ou `/api/v1/simulations` com `{architecture, scenario}` e `scenario.kind` | v0.4 canônico | Validar sem adaptação legada. |
| `/api/v2/*` enquanto existir | v2 existente | Preservar comportamento até migração e testes; não alterá-lo no BE-V4-01. |
| Envelope v2 sem `scenario.kind` enviado a `/api/v1/*` | Formato não canônico nessa rota | Rejeitar com 400 `INVALID_REQUEST`, indicando `scenario.kind`; não inferir versão por campos parcialmente semelhantes. |
| Mistura de `protocol` e `integration`, ou campos inesperados | Ambíguo/inválido | Rejeitar com 400 `INVALID_REQUEST`; não escolher uma interpretação silenciosamente. |

Essa aceitação transitória de corpo v1 na rota v1 deve ser identificada em testes e documentação de migração. O OpenAPI v0.4 descreve apenas o formato canônico; a compatibilidade legada é exceção temporária, com retirada sujeita a decisão posterior e aviso aos consumidores.

## Conversão de uma arquitetura v1 válida

O `ArchitectureValidator` v1 exige exatamente um `CLIENT`, uma `API`, um `DATABASE`, uma aresta `CLIENT → API` com `REST` ou `SOAP` e uma `API → DATABASE` com `TCP`. Só após essa validação é permitido derivar o cenário de simulação.

| Campo legado | Campo canônico | Regra |
| --- | --- | --- |
| `component.id`, `component.type` | mesmos campos | Preservar literalmente. |
| `displayName` ausente | `displayName` | Gerar `Client`, `API` ou `Database` segundo o tipo. Nomes determinísticos, nunca usar truncamento do ID. A origem sintética deve ficar apenas no adaptador/log técnico, sem alegar que veio do cliente. |
| tempos de API/Database | mesmos campos | Preservar valores explícitos. Não aplicar default novo a um payload v1 malformado. |
| `connection.protocol: REST` em `CLIENT → API` | `integration.kind: HTTP_REST` | Sem inventar request/response ilustrativos. |
| `connection.protocol: SOAP` em `CLIENT → API` | `integration.kind: SOAP_HTTP`, `soapVersion: "1.2"` | Política de compatibilidade para a representação ilustrativa; registrar que o v1 não transportava versão SOAP e não há rede/XML real. |
| `connection.protocol: TCP` em `API → DATABASE` | `integration.kind: DATABASE_QUERY` | Conversão **somente** após validar essa topologia v1. Não afirmar que havia SQL no payload; omitir `queryText`/`responseText`. TCP em outra aresta continua inválido. |
| `connection.latencyMs` | mesmo campo | Preservar valor explícito. |

O cenário derivado para `/api/v1/simulations` é `{kind: "REQUEST_RESPONSE", entryComponentId: <CLIENT.id>, entryConnectionId: <id da aresta CLIENT→API>, apiExecutions: [{componentId: <API.id>, dependencyConnectionId: <id da aresta API→DATABASE>}]}`. A derivação é única **apenas** para arquitetura v1 válida segundo o validador legado. Quando a validação v1 falhar, retornar 422 `ARCHITECTURE_INVALID` com as violações existentes; não tentar selecionar um caminho parcial. Para um formato futuro com mais de uma entrada ou dependência, exigir cenário explícito.

## Conversão de v2 e limite global

O corpo v2 `{architecture, scenario}` usa `ScenarioV2` sem `kind`. O cliente v2 deve continuar usando `/api/v2` até ser migrado. Ao migrar o frontend ou dados salvos para `/api/v1`, adicionar `kind: "REQUEST_RESPONSE"` de forma explícita e preservar os demais campos. Os dois exemplos v2 embutidos no OpenAPI passaram no schema v0.4 após essa inclusão; isso não prova todos os payloads v2.

Antes da execução v0.4, validar o teto global de 3.600.000 ms e protegê-lo em runtime. Durações individuais v2 podem ser válidas até 1.000.000.000 ms, portanto a migração pode rejeitar uma execução antes aceita. Não reduzir tempos nem truncar trace. Retornar violação de duração identificável e resultado terminal coerente com API-V4-002.

## Respostas e invariantes de regressão

- Para payload v1 legado, preservar HTTP 200 com `valid=false` na validação de domínio e HTTP 422 `ARCHITECTURE_INVALID` na simulação inválida, além de 400 para sintaxe/tipo inválido.
- O exemplo v1 de referência deve continuar em 260 ms, sete atividades, espera da API de 170 ms e trace em ordem determinística. O resultado canônico acrescentará campos v0.4 sem mudar os tempos ou a causalidade.
- O payload v1 sem Database continua inválido **no modo legado**, mesmo que uma arquitetura canônica v0.4 possa representar API sem Database.
- IDs, latências, tempos e códigos de violação existentes não devem ser alterados pela adaptação. `displayName` sintético é apenas apresentação.

## Casos obrigatórios para BE-V4-02/03

| Caso | Entrada | Esperado |
| --- | --- | --- |
| L1 | v1 de referência REST + TCP em arquitetura direta | Conversão para HTTP_REST + DATABASE_QUERY; cenário único; 260 ms. |
| L2 | v1 SOAP + TCP válido | SOAP_HTTP 1.2 ilustrativo; cenário único; mesma causalidade. |
| L3 | v1 TCP em aresta que não seja API → Database | Violação v1 `INVALID_PROTOCOL`, sem conversão. |
| L4 | v1 sem Database ou com topologia inválida | `valid=false` na validação e 422 na simulação; nenhuma inferência de cenário. |
| L5 | v1 com IDs longos porém válidos, sem `displayName` | Nomes sintéticos cabem no limite de 80 caracteres; IDs preservados. |
| L6 | envelope v2 sem `kind` enviado a `/api/v1/simulations` | 400 `INVALID_REQUEST` com caminho `scenario.kind`. |
| L7 | payload v2 migrado com `kind: REQUEST_RESPONSE` | Aceito pelo schema e execução equivalente quando dentro do limite global. |
| L8 | v2 acima de 3.600.000 ms virtual | Rejeição explícita; sem truncamento ou saturação silenciosa. |
| L9 | payload canônico com API sem Database | Validado pelas regras v0.4, sem aplicar exigência v1 de Database. |

**Dependência:** BE-V4-02 implementa rotas/adaptadores; BE-V4-03 executa estes casos contra backend real. A retirada da aceitação legada e das rotas v2 só ocorre na homologação final, após migração dos consumidores.
