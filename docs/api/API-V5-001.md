# API-V5-001 — Evolução contratual da expansão de serviços

> **Status:** rascunho OpenAPI v0.5.0-contract-draft **não implementado** e **não homologado**. Data: 2026-11-05.
> Base: [CAP-V5-001](../architecture/CAP-V5-001.md), [SEM-V5-001](../architecture/SEM-V5-001.md) e [openapi.yaml](openapi.yaml).
> Não criar endpoints novos: preservar `/api/v1`.

## 1. Escopo inserido no OpenAPI

- 15 tipos: `SERVICE`, `API_GATEWAY`, `BFF`, `WORKER`, `SCHEDULER`, `AUTHENTICATION_SERVICE`, `WEBHOOK_RECEIVER`, `ORCHESTRATOR_SERVICE`, `INTEGRATION_BUS`, `CACHE`, `OBJECT_STORAGE`, `NOTIFICATION_SERVICE`, `SEARCH_ENGINE`, `SERVICE_REGISTRY`, `RULES_ENGINE`.
- `Component.oneOf` e `discriminator` ampliados, mantendo `API`, `DATABASE`, `BROKER` e clientes anteriores.
- `Behavior.trigger` ampliado com `SCHEDULED_TRIGGER`.
- `BehaviorAction.oneOf` ampliado com `BRANCH`, `CACHE_GET`, `CACHE_PUT`, `CACHE_INVALIDATE`, `OBJECT_GET`, `OBJECT_PUT`, `OBJECT_DELETE`, `SEND_NOTIFICATION`, `INDEX_DOCUMENT`, `SEARCH_DOCUMENTS`, `REGISTER_SERVICE`, `UNREGISTER_SERVICE`, `DISCOVER_SERVICE`, `EVALUATE_RULE`, `SCHEDULE_TRIGGER` e `TRANSFORM`.
- Schema de retorno especializado `ResourceOutcomeV5`, schemas de regras declarativas, rotas e agendamentos.
- Exemplo `v5CacheBranchScenario` inserido como exemplo **ilustrativo de contrato**, ainda não executável.

## 2. Escolha provisória para conexão com recurso

**Não foi criado `integration.kind` novo.** Para chamadas a Cache/Object Storage/Search/Registry/Rules, o contrato rascunhado usa `connectionId` explícito associado a uma conexão de request/response **existente** (por exemplo `HTTP_REST` para recursos com interface HTTP simulada). A implementação deve validar a combinação de origem, destino, ação e integração; uma conexão HTTP_REST não implica que todos os recursos executam HTTP real.

Isto é uma decisão **proposta para esta primeira entrega**, não a introdução de um perfil especial `RESOURCE_OPERATION`. Se essa decisão ficar inadequada para Cache/Registry, revisar em ADR antes da implementação.

## 3. Resultados tipados e BRANCH

Ação de recurso pode declarar `outputRef`, e `ResourceOutcomeV5` expõe `resultRef`/ `resultCode` (por exemplo `HIT`, `MISS`, `DENY`).

`BRANCH` recebe `resultRef` e `cases[{equals,actionIds}]`, além de `defaultActionIds?`. O motor precisa validar antes da execução:

- `resultRef` deve ter produtor existente e terminal antes do BRANCH.
- `equals` deve corresponder ao domínio de valores do produtor.
- IDs de ações selecionáveis devem existir no Behavior e não formar ciclos.
- Todas as ações não selecionadas (e seus dependentes não alcançáveis) são marcadas `SKIPPED`, sem execução acidental.
- Ao entrar no ramo MISS, uma Action `CALL` ao Database **não** emite automaticamente RESPOND; um `RESPOND` explícito deve encerrar a requisição.
- Duas respostas concorrentes para o mesmo request são rejeitadas por validação semântica, inclusive após FORK/JOIN.

O esquema OpenAPI valida estrutura básica; validação causal e exclusão de ramos pertencem ao validador Java.

## 4. Estado virtual

Cache, Storage, Search e Registry têm estado isolado por execução, não persistente no servidor. TTL de Cache é avaliado no instante virtual de leitura: `nowMs >= expiresAtMs` produz `MISS`. Para demonstrar hit e miss no mesmo fluxo de simulação, será necessário existir uma sequência explícita de operações agendadas no mesmo contexto.

`SCHEDULER` possui `VirtualScheduleV5` finito, com contagem e intervalo. Cada disparo precisa registrar causalidade no trace e não pode tornar a simulação infinita. A política precisa de testes sobre `mainStatus` e `globalStatus`.

## 5. Delimitações e incompatibilidades pendentes

1. O novo `ResourceOutcomeV5` está **definido como schema**, mas **não integrado ao `SimulationResponse`**. O backend e os testes precisam decidir onde expor resultados de Actions, sem quebrar a resposta v0.4.1.
2. `ActionTrace` existente deve ser estendido para resultado `ResourceOutcomeV5`/novo evento, mantendo os eventos antigos válidos.
3. Para componentes Stateful (Cache, Storage, Search, Registry, Rules), o rascunho define propriedades específicas, mas não adiciona `behaviors` a todos. Esses recursos devem reagir às ações de seus chamadores como recursos especializados; não criar processamento espontâneo.
4. As ações de `TRANSFORM`, `EVALUATE_RULE` e `SCHEDULE_TRIGGER` possuem um schema mínimo. Detalhes de transformação/regras/roteamento, vínculos de autorização e semântica de saída precisam ser refinados antes de implementação.
5. As capacidades dos novos componentes ainda devem ser formalizadas no validador. Não concluir que toda Action permitida no `oneOf` é válida em qualquer tipo de componente.
6. O modelo inicial de Branch compara o `resultCode` a uma string fechada; não interpreta expressões arbitrárias.
7. Não foi criado Load Balancer nem CDN: permanecem no escopo futuro de infraestrutura.
8. Não alterar tipos `API` legados nem renomear automaticamente conexões existentes.
