# API-V6-001 — Contrato técnico proposto para Data Architecture & Processing

> **Status:** especificação técnica de planejamento aprovada quanto à direção de produto; **wire contract ainda sujeito a validação**. Não alterar `docs/api/openapi.yaml` antes do gate contratual.
> **Base:** `docs/api/openapi.yaml` v0.5, `mvp-v0.6.md`, `ADR-V6-001.md`, `DM-V6-001.md`, `UI-V6-001.md`.
> **Invariantes:** `/api/v1`, mesmo relógio virtual, `UnifiedScenario`, causalidade e resposta principal/global.

## 1. Evolução incremental dos endpoints existentes

- `POST /api/v1/architectures/validate`: validar os componentes de dados, perfis de conexão, capacidades e referência dos destinos.
- `POST /api/v1/scenarios/validate`: validar Actions, precedência, pré-condições, cardinalidade e limites do cenário.
- `POST /api/v1/simulations`: produzir execução determinística e resultados tipados de dados.
- Sem `/api/v6`, sem endpoint para executar SQL real e sem persistência de datasets simulados.
- A migração de arquivos locais é feita em cópia e validada antes de alterar o canvas. Não criar endpoint de migração sem necessidade demonstrada; frontend e backend devem aplicar as mesmas regras.

## 2. Componentes e compatibilidade

Expandir `Component.oneOf` e seu `discriminator` com `RELATIONAL_DATABASE`, `DOCUMENT_DATABASE`, `KEY_VALUE_STORE`, `COLUMN_FAMILY_DATABASE`, `GRAPH_DATABASE`, `TIME_SERIES_DATABASE`, `DATA_WAREHOUSE`, `DATA_LAKE`, `ETL_PIPELINE`, `DATA_TRANSFORMER`, `BATCH_PROCESSOR`, `STREAM_PROCESSOR`, `DATA_INGESTION`, `DATA_QUALITY_VALIDATOR`, `CDC_CONNECTOR`. Somente P0 recebe suporte executável inicialmente; schemas de tipos não suportados devem ser mantidos separados do contrato publicamente aceitável até implementar semântica e validação.

`DATABASE` deixa de ser criável e serializável no contrato canônico. A entrada histórica pode ser adaptada explicitamente mediante confirmação ou escolha, **não** por aceitação silenciosa de `DATABASE` no schema novo.

Propriedades específicas de cada discriminador ficam no schema especializado. Os limites máximos devem compartilhar os budgets da execução existente e ser fixados antes do OpenAPI normativo; não aceitar inteiros arbitrariamente grandes.

### 2.1 Fronteira canônica × histórica (decisão 1, 2026-11-07)

A fronteira é o marcador `Architecture.schemaVersion`:

| Documento | Componentes aceitos | Uso |
| --- | --- | --- |
| `schemaVersion: "0.6"` | somente `CanonicalComponentV6` (sem `API` nem `DATABASE`) | criação e exportação v0.6 (editor), validação e simulação |
| sem `schemaVersion` | `Component` (canônicos + `Api`/`Database`, ambos `deprecated: true`) | leitura histórica v0.1–v0.5, inalterada |

A conversão nunca é implícita: passa por `POST /api/v1/architectures/migrate-v6` (MIGRATION-V6-001), que devolve um documento com `schemaVersion: "0.6"`. A regra está no próprio schema (`if/then` em `Architecture`, referenciando `CanonicalComponentV6`), não em comentários.

**Paridade:** `docs/api/examples/v0.6/contract-cases.json` reúne 14 documentos válidos e inválidos (tipos históricos com e sem marcador, tipo P1, versão desconhecida, propriedade ausente ou acima do limite, SQL em Action de dados, `invalidRecordCount` fora de `FILTER_VALID`, transform desconhecido). O `validate.cjs` os valida contra o schema, e o `ContractCasesV6Test` exige que `/api/v1/architectures/validate` aceite e recuse os mesmos.

## 3. Actions V6 e matriz de capacidades P0

Usar `BehaviorAction.oneOf` existente, com schemas discriminados, campos específicos e `additionalProperties: false`. O executor deve rejeitar combinações inválidas ainda que um JSON passe pela sintaxe do schema.

| Tipo / papel | Actions de dados P0 permitidas |
| --- | --- |
| `RELATIONAL_DATABASE` como destino | `DB_SELECT`, `DB_INSERT`, `DB_UPDATE`, `DB_DELETE`, `DB_BULK_INSERT` |
| `DOCUMENT_DATABASE` como destino | `DB_GET`, `DB_PUT`, `DB_FIND`, `DB_UPDATE`, `DB_DELETE`, `DB_BULK_INSERT` |
| `KEY_VALUE_STORE` como destino | `DB_GET`, `DB_PUT`, `DB_DELETE` |
| `ETL_PIPELINE` como executor | `ETL_EXTRACT`, `ETL_TRANSFORM`, `ETL_LOAD` |
| `DATA_TRANSFORMER` como executor | `ETL_TRANSFORM` |
| Serviço chamador compatível | Actions `DB_*` via `connectionId` explícito para um destino de dados compatível |

O executor da Action e o recurso de destino são conceitos diferentes: `DB_SELECT` pertence ao Behavior de um Service/ETL, porém altera/consulta o estado do banco de destino. Não criar Behaviors autônomos no recurso apenas para espelhar chamadas recebidas.

### 3.1 Estrutura ilustrativa de Action

```json
{
  "id": "insert-order",
  "type": "DB_INSERT",
  "connectionId": "service-to-orders-db",
  "dependsOn": [],
  "outputRef": "insertResult",
  "parameters": {
    "collection": "orders",
    "key": "order-001",
    "recordCount": 1,
    "averageRecordBytes": 512
  }
}
```

**Atenção:** exemplo de semântica, não payload garantidamente compatível com o OpenAPI v0.5. Os nomes de `parameters` e `collection` serão reconciliados com os schemas existentes, e não devem ser copiados diretamente como implementação.

- `connectionId` deve resolver uma aresta dirigida do executor até o recurso.
- `dependsOn` preserva grafo acíclico de Actions.
- `outputRef` é único no escopo de Behavior; leitura depende de Action produtora concluída.
- `DB_SELECT/DB_FIND` admitem filtros declarativos fechados de igualdade por campo/chave e limite finito; SQL, JavaScript, expressões e operadores arbitrários são proibidos.
- `DB_UPDATE/DB_DELETE` explicitam política para ausência; nenhuma atualização em massa implícita.
- `DB_BULK_INSERT` opera por lotes agregados e não cria um evento por registro. **O lote é atômico** (decisão 3, 2026-11-07): se não couber inteiro no recurso, nada é gravado (`LIMIT_EXCEEDED`, `rejectedCount` = lote). `PARTIAL` fica reservado e não é produzido em P0. Ver [DATA-BUDGETS-V6-001](../architecture/DATA-BUDGETS-V6-001.md).
- `ETL_EXTRACT` referencia fonte por `connectionId`; `ETL_LOAD` referencia destino; `ETL_TRANSFORM` aplica operadores declarativos e contagens previsíveis. Toda etapa usa `inputRef`/`outputRef` e dependência causal.

Na implementação P0, `IDENTITY` preserva a contagem. `FILTER_VALID` exige `invalidRecordCount` explícito entre zero e a contagem do lote de entrada; a saída contém `inputCount - invalidRecordCount` e `rejectedCount` registra o descarte. Um valor maior que a entrada falha a transformação e impede o LOAD. `NORMALIZE_METADATA` preserva a contagem e marca o lote lógico como normalizado; `normalizedCount` torna esse efeito observável na transformação e no LOAD. Os operadores não executam código de usuário nem inspecionam registros reais.

**Lotes ETL (P0).** O tamanho de lote efetivo é o `batchSize` da Action `ETL_EXTRACT`, quando informado, ou o `batchSize` do `ETL_PIPELINE`. O EXTRACT divide os registros extraídos (`min(registros da fonte, maxRecords)`) em `ceil(registros / batchSize)` lotes lógicos; TRANSFORM e LOAD herdam essa contagem. Se o número de lotes ultrapassar `maxBatches` do pipeline, o EXTRACT termina com `status=FAILED`, `resultCode=LIMIT_EXCEEDED` e `errorCode=ETL_BATCH_LIMIT_EXCEEDED`, sem truncamento silencioso, e o LOAD dependente fica `SKIPPED`. Orçamentos de registros acima de 1.000.000 produzem `errorCode=ETL_RECORD_BUDGET_EXCEEDED` como resultado controlado, nunca exceção. Os campos opcionais `batchCount` e `batchSize` de `DataOperationOutcomeV6` tornam o particionamento observável (adição compatível).

**`DB_UPDATE` (P0).** Atualiza um registro existente; atributos não declarados na Action (`field`/`equals`) são preservados. `DB_INSERT` e `DB_PUT` gravam o registro declarado por inteiro.

## 4. Integrações e transporte

O OpenAPI v0.5 já define `DatabaseQueryIntegration` com `kind: DATABASE_QUERY`. **Preservar esse perfil para compatibilidade**, decidir no gate se ele continua canônico para dados tipados ou se será introduzido perfil adicional. Não rebatizar automaticamente `DATABASE_QUERY` como SQL nem executar `queryText`; o conteúdo é ilustrativo. Caso o perfil seja estendido, validar origem/destino e não converter conexões sem relatório de migração.

Reutilizar perfis síncronos existentes e latência da conexão conforme definição atual; operações de dados são virtuais.

## 5. Resultados tipados e erros

Acrescentar `dataOutcomes` à resposta de `POST /api/v1/simulations` de forma **aditiva**, preservando `resourceOutcomes`, `timeline`, `trace`, `metrics`, `mainStatus` e `globalStatus`. Não renomear os campos existentes.

Campos mínimos conceituais de `DataOperationOutcomeV6`:
`operationId`, `parentOperationId?`, `actionId`, `componentId`, `resourceComponentId`, `connectionId`, `timestampMs`, `startedAtMs`, `completedAtMs`, `queueWaitMs`, `processingMs`, `status`, `resultCode`, `readCount`, `writtenCount`, `rejectedCount`, `logicalBytes`, `outputRef?`, `errorCode?`.

Estados de execução: `SUCCEEDED`, `FAILED`, `TIMED_OUT`, `REJECTED`, `SKIPPED`; códigos de resultado tipados por Action (p.ex. `FOUND`, `NOT_FOUND`, `INSERTED`, `UPDATED`, `LOADED`). Alinhar exatamente com enums implementados do v0.5 antes de publicar contrato.

Erros de validação previstos: `DATA_COMPONENT_UNSUPPORTED`, `DATA_ACTION_INCOMPATIBLE`, `DATA_CONNECTION_INVALID`, `DATA_OUTPUT_REF_INVALID`, `DATA_LIMIT_EXCEEDED`, `DATA_MIGRATION_AMBIGUOUS`. Indicar `componentId`/`actionId`/caminho no erro sem quebrar a estrutura de `ValidationResponse`.

## 6. Segurança, compatibilidade e testes do contrato

- Sem SQL executável; sem credenciais, conexões de banco, payloads reais ou arquivos persistentes.
- Todos os mapas/coleções e metadados sujeitos a `maxItems`, `maxLength`, `maxProperties` e budgets de memória/eventos.
- Importação de v0.1–v0.5 precisa de relatório explícito `DATABASE → RELATIONAL_DATABASE` quando semanticamente compatível, preservando ID e conexões. Em caso de dúvida, não alterar o canvas sem escolha.
- Validar schema OpenAPI 3.1, referências, discriminadores, `oneOf`, `additionalProperties:false`, exemplos válidos e inválidos, geração TypeScript, contrato Java, compatibilidade, replay e limites.
- Cenários mínimos: CRUD write-read, Document FIND, Key-Value GET-PUT-GET, ETL batch, operação inválida, fila limitada, migração e execução determinística.
