# API-V4-003 — Compatibilidade dos contratos v1, v2 e v0.4

**Estado:** revisão documental da Etapa 14. Base: `develop:docs/api/openapi.yaml` (v0.1), `docs/api/openapi-v2.yaml`, `docs/api/openapi.yaml` (rascunho v0.4), controladores e mapeadores Java, clientes e serializadores do frontend na branch `docs/v0.4-communication-profiles-planning`. A compatibilidade descrita aqui ainda requer adaptadores e testes de implementação.

## 1. Situação das rotas

| Operação | Backend atual | Contrato canônico v0.4 | Consequência |
| --- | --- | --- | --- |
| Validar arquitetura | `POST /api/v1/architectures/validate` com arquitetura v0.1; `POST /api/v2/architectures/validate` com arquitetura v2 | `POST /api/v1/architectures/validate` com `Architecture` consolidada | A rota v1 precisa passar a reconhecer o formato novo; clientes v1 antigos precisam de adaptação explícita. |
| Validar cenário | Apenas `POST /api/v2/scenarios/validate` | `POST /api/v1/scenarios/validate` | Implementar a rota v1 antes de migrar o frontend. |
| Simular | `/api/v1/simulations` recebe arquitetura v0.1; `/api/v2/simulations` recebe `{architecture, scenario}` v2 | `/api/v1/simulations` recebe `{architecture, scenario}` v0.4 | Há quebra de formato na mesma rota v1; planejar transição e testes de regressão. |

`ArchitectureController` continua usando `ArchitectureRequestMapper` legado. `V2Controller` usa `V2RequestMapper`. O OpenAPI consolidado **não descreve o comportamento já implementado** da rota v1.

## 2. Matriz de entrada

| Origem | Formato atual | Conversão necessária | Observação |
| --- | --- | --- | --- |
| v0.1/v1 | Arquitetura diretamente no corpo, com `components` e `connections` | Para simular, criar envelope `{architecture, scenario}`; adicionar `displayName` a componentes; converter `connection.protocol` para `connection.integration`; fornecer `scenario.kind`, `entryComponentId`, `entryConnectionId` e `apiExecutions` | A arquitetura v1 antiga não contém escolhas de cenário. Não inferir entrada ou dependência quando houver ambiguidade. |
| v2 | Arquitetura diretamente em validação; envelope em cenário/simulação | Preservar arquitetura e acrescentar `scenario.kind: "REQUEST_RESPONSE"` aos envelopes v2 válidos | `ScenarioV2` não tem discriminador. |
| Frontend atual | `toArchitectureV2()` gera arquitetura v2; `ScenarioDraft` contém entrada e `apiExecutions` | Acrescentar `kind` e migrar cliente para rotas v1 consolidadas; depois suportar variantes WebSocket e Broker | `toArchitectureV2()` transforma os seis tipos visuais de cliente em `CLIENT`; a migração precisa preservar o tipo específico. |
| v0.4 | `Architecture` ou `{architecture, scenario}` conforme endpoint | Nenhuma conversão contratual | Perfis novos e Broker requerem implementação no backend. |

### Conversão de arquitetura v1

- `CLIENT`, `API` e `DATABASE` continuam representáveis, mas o campo `displayName` passa a ser obrigatório. Um adaptador pode usar um nome aprovado pelo produto, mantendo o ID; não deve apresentar isso como dado originalmente enviado pelo cliente.
- `protocol: REST` pode ser representado como `integration.kind: HTTP_REST`; `protocol: SOAP` como `SOAP_HTTP` somente após fornecer `soapVersion: "1.2"` e confirmar a semântica da conexão. `protocol: TCP` **não tem correspondência unívoca** no conjunto novo. Não convertê-lo silenciosamente para `DATABASE_QUERY` sem verificar que a aresta é API → Database e que esse era o sentido pretendido.
- A arquitetura v1 exigia tempos explícitos no decodificador Java. O contrato v0.4 admite omissão de `latencyMs` e tempos da API com default zero; a implementação deverá preservar os valores explícitos dos payloads antigos.
- Para `/simulations`, a escolha de entrada e dependências precisa ser fornecida ou derivada somente quando a topologia deixar uma única possibilidade demonstrável. Definir erro claro para topologia ambígua.

### Conversão de v2

- Os valores `HTTP_REST`, `SOAP_HTTP` e `DATABASE_QUERY`, a estrutura de componentes, `integration`, `apiProcessingOverride`, `entryComponentId`, `entryConnectionId` e `apiExecutions` permanecem representáveis no schema consolidado.
- Nos dois exemplos `simulationRequest` e `scenario` de `openapi-v2.yaml`, o payload original falhou na validação contra `SimulationRequest` v0.4 por ausência de `scenario.kind`. Uma cópia de cada exemplo com `kind: "REQUEST_RESPONSE"` passou no mesmo validador. Isso comprova a conversão **para esses dois exemplos**, não para todos os payloads possíveis.
- Durações v2 individuais podem alcançar 1.000.000.000 ms; a v0.4 limita a execução virtual total a 3.600.000 ms. Um payload v2 válido pode, portanto, deixar de ser executável. Validar o limite global antes e durante a execução e retornar violação explícita.
- A v2 não aceita os novos clientes específicos nem Broker no `V2RequestMapper`; esses dados não devem ser enviados à rota v2 atual.

## 3. Respostas e erros

| Área | Diferença | Trabalho de migração |
| --- | --- | --- |
| Execução | v0.4 exige `execution.mainStatus` além de `status`; admite `COMPLETED_WITH_ERRORS` e `TIMED_OUT` | Atualizar o mapeador de resposta e consumidores do frontend. |
| Trace e métricas | v0.4 amplia estados, atividades, métricas por perfil, representações e correlação | Preservar campos v2 aplicáveis; gerar novos campos somente quando há semântica correspondente. |
| Exemplo v1 de 260 ms | O JSON original não atendia ao novo `SimulationResponse`; foi atualizado em `scenario-260ms.json` | O exemplo atualizado é evidência de formato, não prova de que o backend atual o emite. |
| Erros HTTP | A v2 usa `application/problem+json` para simulação inválida (422); a v1 atual tem outro fluxo | Alinhar códigos, corpo e media type ao OpenAPI v0.4; manter testes de regressão de 400/413/415/422/500. |

## 4. Sequência recomendada de implementação

1. Definir e testar o adaptador de entradas legadas v1, incluindo política explícita para `TCP` e para cenários ambíguos. Não aceitar duas formas públicas indefinidamente sem uma política de retirada.
2. Migrar o mapeador v2 para o modelo canônico, incluindo `REQUEST_RESPONSE` e os clientes específicos; acrescentar WebSocket e Broker em seguida.
3. Implementar as três rotas `/api/v1` do contrato consolidado e os mapeadores de resposta/erro.
4. Atualizar o frontend para serializar o tipo real dos seis clientes, usar `scenario.kind` e chamar `/api/v1`; acrescentar edição dos novos perfis e cenários.
5. Executar regressões com payloads v1/v2 reais, exemplos v0.4, casos negativos, limite global e respostas. Só então retirar rotas `/api/v2` e o contrato v2 ativo.

## 5. Limite desta revisão

Esta etapa comparou contratos e código e validou os dois exemplos v2 citados contra o schema v0.4 após a conversão. Não executou requisições contra o backend nem provou compatibilidade comportamental. A implementação permanece pendente.
