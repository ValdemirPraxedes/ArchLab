# API-V4-002 — Schemas, limites, defaults e erros do contrato v1

> **Status: decisões contratuais aprovadas em 2026-11-04.** Esta especificação fixa diretrizes, valores de limite e defaults da v0.4. A tradução integral para OpenAPI 3.1 em `docs/api/openapi.yaml`, a validação de `oneOf`, os exemplos e os DTOs finais ainda são **tarefas técnicas pendentes**. Nenhum endpoint foi alterado por este documento.
>
> Referências: [API-V4-001](API-V4-001.md), [DM-V4-001](../architecture/DM-V4-001.md), [VAL-V4-001](../architecture/VAL-V4-001.md), [ADR-V4-006](../architecture/ADR-v0.4.md), [Requisitos v0.4](../requirements/mvp-v0.4.md).

## 1. Escopo e versões

- **Somente uma API pública** com prefixo `/api/v1`, depois de concluir a migração da v2.
- OpenAPI 3.1 como contrato canônico em `docs/api/openapi.yaml`; não criar `/api/v4` nem `openapi-v4.yaml` públicos.
- Endpoints-alvo: `POST /api/v1/architectures/validate`, `POST /api/v1/scenarios/validate` e `POST /api/v1/simulations`.
- Preservar recursos de v1, v2 e v0.3; investigar incompatibilidades antes de retirar as rotas `/api/v2/**`.

## 2. Organização dos schemas

| Grupo | Schemas lógicos | Responsabilidade |
| --- | --- | --- |
| Arquitetura | `Architecture`, `Component`, `Connection` | Grafo, IDs, participantes, arestas, latência |
| Componentes | `Client`, `Api`, `Database`, `Broker` | Tipos visuais, propriedades e configuração de destinos lógicos |
| Integração | `Integration` e variantes discriminadas | Semântica específica dos perfis |
| Execução | `SimulationRequest`, `Scenario` e variantes | Uma operação principal, origem e parâmetros |
| Resultado | `Execution`, `InitialState`, `TraceEntry`, `TimelineActivity`, `Metrics`, `MessageRepresentation` | Conclusão principal/global, causalidade e playback |
| Erros | `Problem`, `Violation` | Erros de formato, domínio, configuração e limites |

Os nomes acima são **nomes de schemas de contrato**, não exigência de classes Java com a mesma nomenclatura. A modelagem interna do core permanece independente do adaptador REST.

## 3. Componentes e compatibilidade

O contrato canônico deve reconhecer `WEB_BROWSER`, `MOBILE_APP`, `DESKTOP_APP`, `CLI`, `BOT` e `EMBEDDED_SYSTEM`; o tipo `CLIENT` original será tratado durante a migração. Os tipos `API`, `DATABASE` e `BROKER` continuam conforme DM-V4-001. Não introduzir outros nós.

`Component` inclui identidade e nome de apresentação, além de propriedades específicas. `Connection` preserva `id`, `sourceId`, `targetId`, `latencyMs`, `integration`, e configurações compatíveis de versões anteriores quando cabíveis. A configuração do Broker deve relacionar fila/tópico lógico, inscrição e conexões reais; nenhum destino lógico cria nó de canvas.

## 4. União discriminada de integrações

`Integration` será uma união OpenAPI 3.1 `oneOf` com discriminador explícito `kind`. Cada variante tem um valor exclusivo, campos relevantes e requisitos/validações próprios. Preservar os valores de integração legados `HTTP_REST`, `SOAP_HTTP` e `DATABASE_QUERY` para facilitar migração.

| Perfil | `integration.kind` aprovado | Campos semânticos mínimos |
| --- | --- | --- |
| REST | `HTTP_REST` | Método HTTP, caminho; compatibilidade com representação legada quando aplicável |
| SOAP | `SOAP_HTTP` | Operação, ação opcional e propriedades legadas pertinentes |
| HTTP genérico | `HTTP_GENERIC` | Método HTTP, caminho |
| GraphQL HTTP | `GRAPHQL_HTTP` | `operationType` QUERY/MUTATION, nome da operação |
| gRPC unary | `GRPC_UNARY` | Serviço e método |
| CoAP | `COAP` | Método, recurso, modo CON/NON |
| WebSocket | `WEBSOCKET` | Caminho, timeouts, mensagens direcionadas, intervalos e fechamento |
| MQTT | `MQTT` | Tópico e QoS 0 |
| Queue Messaging | `QUEUE` | Fila lógica |
| Topic Messaging | `TOPIC` | Tópico lógico |
| Compatibilidade API → Database | `DATABASE_QUERY` | Propriedades de consulta já existentes; **não conta** como um dos dez perfis |

A matriz aprovada DEC-06/VAL-V4-001 continua sendo autoridade para validação das ligações. `oneOf` não deve conter variantes estruturalmente ambíguas; verificar `required`, `const` e mapping do discriminador. Não exigir protocolo de rede real, schemas GraphQL, `.proto` ou execução real de SQL.

### Exemplo ilustrativo de integração GraphQL

```json
{
  "id": "conn-1",
  "sourceId": "client-1",
  "targetId": "api-1",
  "latencyMs": 50,
  "integration": {
    "kind": "GRAPHQL_HTTP",
    "operationType": "QUERY",
    "operationName": "GetOrders"
  }
}
```

O trecho é ilustrativo; **não substitui um exemplo validado do futuro OpenAPI**.

## 5. Cenário de execução

`SimulationRequest` preserva o agrupamento:

```json
{
  "architecture": {},
  "scenario": {
    "kind": "REQUEST_RESPONSE",
    "entryComponentId": "client-1",
    "entryConnectionId": "conn-1",
    "apiExecutions": []
  }
}
```

As três variantes aprovadas de `scenario.kind` são:

| `kind` | Objetivo | Restrições |
| --- | --- | --- |
| `REQUEST_RESPONSE` | Requisição síncrona e suas dependências | Preservar os dados de execução de APIs existentes; compatível com perfil de entrada |
| `WEBSOCKET_SESSION` | Abrir, trocar mensagens bidirecionais e fechar uma sessão | Uma sessão por conexão por execução; mensagens finitas |
| `MESSAGE_PUBLISH` | Publicar/enviar a Queue, Topic ou MQTT por Broker | Um evento principal, entregas derivadas finitas |

Preservar `entryComponentId` e `entryConnectionId` onde semanticamente válidos. `apiExecutions` e outras estruturas legadas devem ser reconciliadas antes do schema definitivo. Para payloads antigos sem `scenario.kind`, uma adaptação **explícita e testada** poderá ser empregada durante migração; não mudar o sentido do cenário silenciosamente.

## 6. Limites aprovados

| Recurso | Valor aprovado | Aplicação |
| --- | ---: | --- |
| Componentes por arquitetura | **1.000** | Máximo por arquitetura |
| Conexões por arquitetura | **3.000** | Máximo por arquitetura |
| Mensagens por sessão WebSocket | **100** | Máximo por sessão |
| Mensagens publicadas por simulação | **100** | Máximo global de publicações |
| Assinaturas por tópico | **100** | Máximo de assinaturas elegíveis por tópico |
| Entregas derivadas por simulação | **1.000** | Máximo de entregas originadas por operações |
| Eventos processados por execução | **50.000** | Limite de proteção do motor |
| Duração virtual máxima | **3.600.000 ms** | Uma hora virtual por simulação |
| Timeout padrão de Queue sem consumidor | **30.000 ms** | Espera finita antes de resultado terminal explícito |
| Profundidade de operações derivadas | **32** | Limite de propagação causal |

Limites de campos, tamanho de payload lógico e detalhes de contagem/estouro **ainda requerem especificação técnica**, sem alterar estes números aprovados. Os limites operacionais devem ter validações pré-execução quando possível e proteção em runtime quando a quantidade depender de fan-out. Exceder o limite não pode levar a execução infinita ou truncamento silencioso; registrar o motivo adequadamente.

**Nota de compatibilidade:** o contrato v2 existente permitia até `1.000.000.000 ms` por propriedade de duração. O novo **limite global de 3.600.000 ms** não equivale à mesma restrição e pode exigir migração documentada de cenários antes aceitos. Determinar como validar a duração total prevista e lidar com término em execução no contrato técnico.

## 7. Defaults aprovados

| Campo/condição | Valor padrão | Observações |
| --- | --- | --- |
| Latência da conexão | **0 ms** | Aplicar no backend quando omitido e permitido no schema; preservar payload legado |
| Processamento do componente | **0 ms** | Aplicar quando a propriedade for opcional; não reescrever comportamento legado sem teste |
| Timeout de abertura WebSocket | **5.000 ms** | Tempo virtual |
| Timeout por inatividade WebSocket | **desabilitado** | Diferenciar ausência de zero e de valor explícito |
| Intervalo entre mensagens WebSocket | **0 ms** | Desempate determinístico obrigatório |
| Fechamento da sessão WebSocket | **automático após sequência** | Fechamento explícito também é permitido conforme DEC-09 |
| Modo CoAP | **CON** | Distinguir CON/NON e confirmação quando aplicável |
| QoS MQTT | **0** | Outros QoS fora do escopo |
| Espera Queue sem consumidor | **30.000 ms** | Resultado terminal rastreável |

Os defaults aplicáveis devem ser definidos **no contrato e no backend**, sem depender só da UI. O schema precisa deixar clara a obrigatoriedade e a semântica de omissão, inclusive em adaptadores de compatibilidade. Validações de timeout e fecho não podem gerar mensagens de aplicação após falha de abertura.

## 8. Estados finais e formato de resultados

Preservar a estrutura pública de resultado:

```json
{
  "execution": {},
  "initialState": {},
  "trace": [],
  "timeline": [],
  "metrics": {},
  "messageRepresentations": []
}
```

Os quatro valores de resultado global aprovados são:

| `execution.status` | Semântica |
| --- | --- |
| `COMPLETED` | Execução global concluída com sucesso |
| `FAILED` | Execução global concluída com falha |
| `TIMED_OUT` | Execução global encerrada por timeout |
| `COMPLETED_WITH_ERRORS` | Execução finalizada com falhas parciais ou pendências terminalizadas |

A estrutura deve conservar o estado da operação principal **separado** do resultado global, com status e correlação necessários. `execution.mainStatus` é um nome candidato para a representação pública, a confirmar no schema OpenAPI final.

Os eventos e as métricas precisam distinguir aceitação, entrega simulada, processamento, espera, sessão aberta/fechada, timeout e término de operações derivadas. Não interpretar QoS 0 como entrega garantida.

Exemplo ilustrativo:

```json
{
  "execution": {
    "id": "execution-1",
    "status": "COMPLETED_WITH_ERRORS",
    "mainStatus": "COMPLETED",
    "totalDurationMs": 350
  }
}
```

## 9. HTTP e Problem Details

| HTTP | Situação |
| --- | --- |
| **200** | Validação executada ou simulação corretamente processada, **inclusive quando o resultado virtual é uma falha/timeout semântico** |
| **400** | JSON malformado ou schema ilegível/inválido |
| **413** | Corpo acima do limite de tamanho permitido |
| **415** | Tipo de mídia não suportado |
| **422** | Domínio/cenário inválido para execução |
| **500** | Falha inesperada real no backend/motor |

Preservar **Problem Details (RFC 9457)** para erros HTTP: `type`, `title`, `status`, `detail`, `instance`, código estável `code` e `violations[]` com `code`, `path` e `message`, quando aplicável.

Códigos iniciais aprovados:
- `INVALID_CONNECTION_PROFILE`;
- `INVALID_SUBSCRIPTION`;
- `EXECUTION_LIMIT_EXCEEDED`;
- `INVALID_SCENARIO`.

Outros códigos e caminhos de erro devem ser adicionados de forma consistente, sem inventar status HTTP distintos para falhas semânticas virtuais. O endpoint `architectures/validate` pode responder `200` com `valid: false` para violações de domínio seguindo a convenção existente; a simulação de entrada inválida utiliza `422` conforme contrato.

## 10. Validação técnica obrigatória para promover ao contrato executável

1. Converter esta especificação em OpenAPI 3.1 em `docs/api/openapi.yaml`, preservando os três endpoints públicos.
2. Definir `required`, `additionalProperties`, limites por campo, `oneOf`, mappings de discriminador e schemas de erros/respostas sem duplicações ambíguas.
3. Definir modelos completos de Broker, destinos lógicos, assinaturas, mensagens WebSocket, operações e estados derivadas.
4. Documentar explicitamente diferenças de payload e de limites entre v1, v2 e v0.4 e a estratégia de adaptação.
5. Validar sintaxe, `$ref`, discriminadores e exemplos; gerar tipos TypeScript; implementar/testar DTOs Java.
6. Testar todas as famílias de perfil, cenários inválidos, falhas/timeout, determinismo, limites e regressões v0.1–v0.3.
7. Migrar consumidores antes de remover publicamente `/api/v2/**`. Não remover a infraestrutura interna da v2 sem verificar reutilização.
