# API-V4-001 — Contrato canônico da API pública v1 (planejamento v0.4)

> **Status: diretrizes de contrato aprovadas em 2026-11-04.** Esta especificação é **preliminar e não executável**. As estruturas JSON deste documento são ilustrativas; **não** são um schema OpenAPI homologado. Contrato público canônico futuro: `docs/api/openapi.yaml`. **Não alterar esse YAML até definir schemas, validações, códigos de erro e limites.**

## 1. Contexto e referências

- [Requisitos da v0.4](../requirements/mvp-v0.4.md), especialmente **RF-V4-001 a RF-V4-025**.
- [ADR-V4-006](../architecture/ADR-v0.4.md) — consolidar as APIs públicas somente em `/api/v1`.
- Contratos existentes para comparação: [OpenAPI v1](openapi.yaml) e [OpenAPI v2](openapi-v2.yaml).
- A versão do produto (v0.4) **não** determina novo prefixo de URL.

A v1 original tinha `POST /api/v1/architectures/validate` e `POST /api/v1/simulations`; a v2 inclui ainda `POST /api/v2/scenarios/validate`, modelo de cenário explícito, integrações discriminadas e representação de mensagens. A migração deve manter capacidades funcionais e identificar mudanças incompatíveis, não somente renomear rotas.

## 2. Decisões contratuais aprovadas

1. **Um contrato público canônico** em `docs/api/openapi.yaml`, com rotas exclusivamente `/api/v1` ao fim da migração; não criar `/api/v4`.
2. Adotar o **modelo funcional mais expressivo da v2 como referência**, sem carregar sufixos `V2` para os nomes canônicos.
3. Reconhecer diretamente na API unificada os **seis tipos visuais de cliente** (`WEB_BROWSER`, `MOBILE_APP`, `DESKTOP_APP`, `CLI`, `BOT`, `EMBEDDED_SYSTEM`), mantendo a interpretação de `CLIENT` legado durante a migração.
4. Modelar os **dez perfis** com uma união discriminada de integrações identificadas por `kind`.
5. Preservar a separação `architecture` / `scenario` no pedido de simulação.
6. Evoluir os resultados mantendo os agrupamentos existentes `execution`, `initialState`, `trace`, `timeline`, `metrics`, `messageRepresentations` e seus dados já úteis, sempre que possível.
7. Migrar o frontend e demais consumidores conhecidos, testar contratos e cenários legados e **retirar os endpoints `/api/v2` somente ao concluir a migração**.
8. Usar adaptações temporárias quando necessário; registrar explicitamente incompatibilidades reais. **Não prometer retrocompatibilidade automática só por reutilizar `/api/v1`.**

## 3. Endpoints públicos-alvo

| Método | Rota | Responsabilidade |
| --- | --- | --- |
| POST | `/api/v1/architectures/validate` | Validar componentes, identidades, conexões e compatibilidade dos perfis, inclusive arquiteturas incompletas quando cabível |
| POST | `/api/v1/scenarios/validate` | Validar arquitetura e o cenário/operação inicial sem executar |
| POST | `/api/v1/simulations` | Validar, simular e devolver resultado completo para playback |

A tabela define a **intenção aprovada**; variações de compatibilidade e DTOs ainda precisam de especificação. Não criar rotas `/api/v4`, e não manter rotas públicas `/api/v2` após a migração validada.

## 4. Modelo lógico de arquitetura

### 4.1 Componentes

Tipos canônicos de cliente aprovados: `WEB_BROWSER`, `MOBILE_APP`, `DESKTOP_APP`, `CLI`, `BOT`, `EMBEDDED_SYSTEM`; preservar `CLIENT` legado para migração. Componentes existentes `API` e `DATABASE` permanecem; adicionar `BROKER`.

- Identidades (`id`) e nomes (`displayName`) precisam continuar correlacionáveis entre editor, pedido e resultado.
- Componentes de API conservam propriedades relevantes de processamento.
- Broker possui configuração de destinos lógicos e assinaturas **a definir formalmente**.
- O enum de tipos do domínio/DTO deverá ser revisado, sem exigir alteração prematura da modelagem interna.
- A conversão visual específica → `CLIENT` da v0.3 será desnecessária no **contrato canônico da v0.4**, mas poderá permanecer em adaptadores de compatibilidade durante a migração.

### 4.2 Conexões

Conservar `id`, `sourceId`, `targetId`, `latencyMs` e um objeto `integration`. O campo `integration.kind` identifica o perfil semântico. Campos de timeout, overrides de processamento, semântica de retorno, subscriptions e limites específicos serão especificados posteriormente, respeitando a matriz de compatibilidade aprovada.

**Não** repetir propriedades comuns em cada variante quando não necessário. Preservar ligação de API → DATABASE conforme a integração de banco existente, que não conta como um dos dez perfis de comunicação da v0.4.

### 4.3 Exemplo ilustrativo, **não-validado**

```json
{
  "components": [
    {"id": "client-1", "type": "WEB_BROWSER", "displayName": "Navegador"},
    {"id": "api-1", "type": "API", "displayName": "Pedidos API", "preProcessingMs": 20, "postProcessingMs": 10}
  ],
  "connections": [
    {
      "id": "conn-1",
      "sourceId": "client-1",
      "targetId": "api-1",
      "latencyMs": 50,
      "integration": {"kind": "REST", "method": "GET", "path": "/orders"}
    }
  ]
}
```

**Atenção:** os nomes `kind: REST` e os campos exemplificados não substituem a definição normativa de `oneOf`, `discriminator` e propriedades requeridas.

## 5. Integrações discriminadas

| `kind` proposto | Configurações essenciais | Semântica |
| --- | --- | --- |
| `REST` | Método HTTP, caminho | Requisição/resposta REST |
| `SOAP` | Operação, ação opcional | Requisição/resposta SOAP |
| `HTTP_GENERIC` | Método HTTP, caminho | Requisição/resposta HTTP genérica |
| `GRAPHQL_HTTP` | Query/Mutation, nome de operação | Operação GraphQL sem parser/schema real |
| `GRPC_UNARY` | Serviço, método | Uma requisição RPC e uma resposta |
| `COAP` | Método, recurso, CON/NON | Confirmação semântica quando aplicável |
| `WEBSOCKET` | Caminho, timeouts, sequência/direção/intervalo de mensagens | Sessão virtual bidirecional |
| `MQTT` | Tópico, QoS 0 | Publicação/assinatura com correspondência exata |
| `QUEUE` | Nome de fila | Uma entrega por mensagem a consumidor elegível |
| `TOPIC` | Nome de tópico | Uma entrega por assinatura elegível |

Além dessas variantes, a integração de consulta ao Database existente deve ser **preservada por compatibilidade**; não constitui um décimo primeiro perfil do escopo da v0.4.

Os identificadores discriminadores listados são **candidatos aprovados como desenho lógico**, ainda sujeitos ao fechamento de enums/compatibilidade com identificadores existentes como `HTTP_REST` e `SOAP_HTTP`.

## 6. Pedido de simulação e cenário

O pedido canônico mantém a forma lógica:

```json
{"architecture": {}, "scenario": {}}
```

O cenário deve representar:
- Chamada inicial de requisição/resposta, que pode partir de Cliente ou API conforme regras permitidas;
- Início de sessão WebSocket em Cliente → API ou API → API;
- Publicação/envio de mensagem com destino lógico no Broker.

Preservar `entryComponentId` e `entryConnectionId` onde semanticamente aplicáveis, sem forçar configuração de HTTP em operações WebSocket ou mensagens. Preservar e evoluir os recursos de `apiExecutions` existentes, identificando compatibilidades e conflitos na especificação normativa.

**Pendente:** forma exata do discriminador do tipo de cenário, obrigatoriedades, cardinalidades, dependências, seleção de operação e limites de quantidades.

## 7. Resultado da simulação

A resposta canônica mantém, como agrupamentos lógicos, os campos:

```json
{
  "execution": {},
  "initialState": {},
  "trace": [],
  "timeline": [],
  "metrics": {},
  "messageRepresentations": []
}
```

- `execution`: resultado/status da operação principal e da conclusão global, durações e identificação.
- `initialState`: componentes, sessões e recursos relevantes no instante inicial, conforme aplicável.
- `trace`: eventos determinísticos, participantes, perfil e correlação com operação/mensagem/sessão.
- `timeline`: períodos e eventos associados a chamadas, sessões, publicações, entregas e processamento.
- `metrics`: tempos de processamento/comunicação e métricas específicas para requisição/resposta, WebSocket e mensageria.
- `messageRepresentations`: representação lógica de mensagens, sem payload real de rede.

Os atuais status de execução documentados como `COMPLETED` precisam ser ampliados, quando necessário, para representar **falha, timeout e encerramento com pendências**, sem equiparar terminal a sucesso. Correlacionar conclusão principal e global conforme DEC-11.

**Pendente:** variantes `oneOf`, nomes definitivos de eventos e status, campos obrigatórios, IDs, limites e compatibilidade exata de retorno.

## 8. Migração da v2 e compatibilidade da v1

### 8.1 Inventário obrigatório antes de alterar endpoints

| Área | v1 original | v2 | Ação de reconciliação |
| --- | --- | --- | --- |
| Rotas | Validar arquitetura e simular | Validar arquitetura, validar cenário, simular | Consolidar os três endpoints em `/api/v1` |
| Grafo | Restrições originais de Client/API/Database | Grafo ampliado, DAG e cenário explícito | Preservar funcionalidades do cenário v0.3 |
| Conexão | `protocol` | `integration` | Definir conversão/adaptação, sem perda silenciosa |
| Componentes | Modelo original sem nomes em todos os tipos | `displayName` e dados de API | Tratar nomes/valores ausentes em payloads legados |
| Pedido de simulação | Formato original `ArchitectureRequest` | `{architecture, scenario}` | Testar convivência ou migração, registrar breaking changes |
| Resultado | Execução, estados, trace, timeline, métricas | Acrescenta `messageRepresentations` e correlações | Preservar playback e métricas legadas |
| Erros | Códigos e formatos do contrato v1 | Contrato v2 distinto | Unificar Problem Details e tratamento de validação |

### 8.2 Sequência de migração obrigatória

1. Levantar consumidores internos e, quando identificáveis, externos, incluindo frontend e testes.
2. Definir contrato canônico v1 e estratégia explícita de adaptação para payloads antigos.
3. Implementar e testar endpoints v1 com as capacidades hoje disponíveis na v2.
4. Migrar frontend/consumidores conhecidos para v1.
5. Executar testes de contrato, integração e regressão dos cenários v0.1, v0.2 e v0.3.
6. **Somente após comprovação**, retirar controladores, rotas e especificação pública ativa da v2.
7. Expandir o mesmo contrato v1 para os recursos v0.4, sem criar nova versão pública.

A remoção de uma rota v2 não obriga apagar código interno útil que contenha sufixo `V2`; refatoração de nomes é decisão técnica separada.

**Refinamento aprovado na Etapa 11:** [API-V4-002 — Schemas, limites, defaults e erros](API-V4-002.md) prevalece sobre referências anteriores a valores numéricos, discriminadores e códigos de resultado ainda pendentes. A tradução para OpenAPI 3.1 completo continua por realizar.

## 9. Pendências para tornar o OpenAPI normativo

- Validações e limites: IDs, cardinalidade de nós/arestas, conexões, mensagens, filas, tópicos, assinaturas, tempo virtual, timeouts.
- Enums finais dos tipos, discriminadores, métodos e estados; `oneOf` sem ambiguidades.
- Schema do Broker e sua configuração lógica, de inscrições e consumidores.
- Schema da sequência de mensagens WebSocket, direções, intervalos e encerramento.
- Schema do cenário de execução e sua compatibilidade com `ScenarioV2`.
- Contratos de resultado, correlação, trace, timeline, métricas, falhas e conclusão principal/global.
- Códigos de violação e status HTTP para validação, erro do cenário, tipo não suportado e falha inesperada.
- Plano de adaptação de contratos legados e matriz de testes de regressão por endpoint.
- Validação de OpenAPI 3.1, geração de tipos e exemplos JSON **após** a aprovação do schema normativo.
