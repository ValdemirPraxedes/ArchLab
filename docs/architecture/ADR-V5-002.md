# ADR-V5-002 — Resultados tipados, BRANCH e recursos virtuais

> **Status:** proposta normativa para revisão do PR de documentação. Complementa [ADR-V5-001](ADR-V5-001.md), [SEM-V5-001](SEM-V5-001.md) e [API-V5-001](../api/API-V5-001.md). Nenhum código Java/React alterado.

## Decisões

### 1. Resultado tipado por Action

Ações especializadas produzem um `ResourceOutcomeV5` com `actionId`, `status`, `resultCode`, `resultRef?`, `timestampMs?`, `operationId?`, `componentId?`, `connectionId?` e `details?` limitado a metadados escalares. O `resultRef` é a chave para dependência de Actions e deve ser único no escopo do Behavior ou da operação; nenhum resultado é compartilhado entre simulações diferentes.

O campo `SimulationResponse.resourceOutcomes[]` é **opcional** para preservar respostas antigas; `ActionTrace.outcome?` permite observar o resultado no instante virtual correspondente. A mesma ação não pode emitir dois resultados terminais conflitantes. Falhas dinâmicas não viram erro 500 automaticamente. Não incluir dados privados reais, anexos ou arquivos.

### 2. BRANCH com exclusão explícita

`BRANCH` compara o `resultCode` de uma ação predecessora à chave `equals` das alternativas configuradas. Cada alternativa indica `actionIds[]` pertencentes ao mesmo Behavior; a seleção ativa apenas um conjunto. Os demais ramos passam a `SKIPPED` no trace e não podem causar efeitos.

- Validar `resultRef` existente, único e produzido por predecessor terminal.
- Cada `equals` deve ser única no mesmo BRANCH.
- Não aceitar overlap de `actionIds` entre branches mutuamente exclusivas.
- IDs alvo não podem ser predecessores do próprio BRANCH nem produzir ciclo.
- `defaultActionIds?` é aplicado somente se não houver correspondência; se ausente, o Behavior encerra com evento sem ramo selecionado, sujeito às invariantes de resposta.
- Se `resultCode` estiver indisponível devido a falha/timeout, o motor deve aplicar uma política explícita de erro, e **não** tratá-lo como MISS.
- Ações dependentes de elementos `SKIPPED` permanecem SKIPPED, exceto um join/merge explicitamente definido como capaz de aceitar ramos alternativos.
- `RESPOND` em ramos exclusivos é válido desde que somente um possa ser alcançado para cada contexto de request. Dois RESPOND atingíveis simultaneamente são inválidos.

Exemplo `CACHE_GET → BRANCH`: HIT seleciona `respond-hit`; MISS seleciona `db-read` e `respond-miss`, este último dependente de `db-read`. Não executar `db-read` e `respond-hit` juntos.

### 3. Conexões de recursos e perfis

A primeira proposta de implementação utiliza uma **conexão dirigida explícita** com um perfil de requisição/resposta existente (por exemplo, HTTP_REST ou HTTP_GENERIC) para operações lógicas de Cache, Object Storage, Search Engine, Registry e Rules Engine. A semântica da operação deriva de `BehaviorAction.kind` e do tipo de destino. O validador rejeita `CACHE_GET` apontando para `OBJECT_STORAGE` ou uma conexão `QUEUE` sem capacidade adequada.

Isso **não** significa que Redis, S3 ou um Registry executem HTTP real; é uma abstração didática. A extensão para `RESOURCE_OPERATION` separado permanece fora da v0.5 inicial. `DATABASE_QUERY` continua reservado à Database conforme matriz atual.

### 4. Estado virtual

O estado dos recursos é restrito à execução corrente, com atualizações ordenadas no mesmo clock e scheduler determinístico. Para Cache, TTL expira no instante `nowMs >= expiresAtMs`; put com TTL=0 nunca é HIT. Para Search, o documento indexado fica visível ao terminar INDEX_DOCUMENT. Registry não cria arestas automaticamente. Storage mantém metadados e tamanho, não bytes do objeto. Tudo tem budget finito.

### 5. Scheduler e operação principal

`SCHEDULED_TRIGGER` é produzido por um Scheduler configurado com `firstAtMs`, `intervalMs` e `occurrenceCount` finitos. Cada disparo tem identidade causal estável. O cenário determina uma operação raiz única e rastreia disparos filhos; `mainStatus` acompanha a raiz, `globalStatus` só termina após os filhos relevantes. Não usar cron externo nem job em background real.

### 6. Compatibilidade

Manter `API`, `Broker`, `Database`, todos os tipos de Client, `Scenario` legado e `UnifiedScenario`. Os schemas novos são aditivos e seus campos opcionais não podem tornar os exemplos antigos inválidos. Nenhum endpoint `/api/v5`. Não converter `API` em `SERVICE` silenciosamente.
