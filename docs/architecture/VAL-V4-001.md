# VAL-V4-001 — Regras de validação, invariantes e limites da v0.4

> **Status:** regras VAL-V4-001 a VAL-V4-010 aprovadas em 2026-11-04. **Limites numéricos e defaults aprovados posteriormente em [API-V4-002](../api/API-V4-002.md); este documento mantém a tabela histórica de pendências da etapa 10.** Os schemas completos ainda precisam ser codificados e validados. Documento de planejamento, sem autorização de implementação.
>
> Referências: [requisitos da v0.4](../requirements/mvp-v0.4.md), [modelo de domínio](DM-V4-001.md), [decisões arquiteturais](ADR-v0.4.md), [contrato preliminar](../api/API-V4-001.md).

## 1. Princípios

A validação do frontend pode antecipar erros de UX, mas o backend deve validar as mesmas invariantes de domínio antes de iniciar o motor. Não modificar o grafo para contornar violações, converter silenciosamente protocolos incompatíveis ou descartar mensagens inválidas. Preservar as regras existentes da v0.3 salvo quando explicitamente evoluídas na v0.4.

A validação de **arquitetura** verifica componentes, conexões e configurações; a validação de **cenário** verifica uma execução selecionada sem executá-la. O simulador revalida entradas antes da execução.

## 2. Regras aprovadas

| ID | Regra normativa | Comportamento esperado |
| --- | --- | --- |
| **VAL-V4-001** | IDs de componentes e conexões não vazios e únicos em seu domínio | Rejeitar duplicidade/identidade inválida; preservar IDs durante a execução |
| **VAL-V4-002** | Toda conexão referencia componentes existentes | Rejeitar origem/destino ausentes e referências inconsistentes |
| **VAL-V4-003** | O perfil de integração é compatível com os tipos de origem/destino | Aplicar a matriz aprovada DEC-06; rejeitar Cliente → Database, Broker → Broker e perfis incompatíveis |
| **VAL-V4-004** | Cada variante de integração possui propriedades válidas para seu `kind` | Rejeitar campos obrigatórios faltantes, configuração incompatível e discriminadores desconhecidos |
| **VAL-V4-005** | Toda sessão WebSocket tem sequência finita de mensagens | Validar início, direção, intervalos, condições de encerramento e limites; a sessão não pode executar indefinidamente |
| **VAL-V4-006** | Publicações/entregas do Broker referenciam destinos lógicos existentes e compatíveis | Validar nomes, fila/tópico e coerência de perfil; não inventar destino inexistente |
| **VAL-V4-007** | Assinaturas referenciam APIs consumidoras e conexões elegíveis | Rejeitar assinatura inválida ou divergente do grafo |
| **VAL-V4-008** | Durações, latências e intervalos não são negativos | Aceitar zero se semanticamente válido; rejeitar números inválidos/overflow |
| **VAL-V4-009** | A operação inicial é válida para o cenário e a conexão selecionada | Rejeitar entrada inexistente, incompatibilidade de modalidade e configurações que não podem executar |
| **VAL-V4-010** | Cenários respeitam limites e determinismo | Rejeitar operações infinitas, excesso de recursos/eventos e condições que impedem terminação |

## 3. Matriz aprovada de conexão

| Perfil | Cliente → API | API → API | Cliente → Broker | API → Broker | Broker → API |
| --- | --- | --- | --- | --- | --- |
| REST, SOAP, HTTP genérico, GraphQL, gRPC unary, CoAP | Sim | Sim | Não | Não | Não |
| WebSocket | Sim | Sim | Não | Não | Não |
| MQTT, Queue, Topic | Não | Não | Sim | Sim | Sim |

- `API → Database` permanece com a integração existente, fora dos dez perfis.
- `Cliente` significa todos os seis tipos da v0.3 (e o legado `CLIENT` durante migração).
- Na aresta `Broker → API`, a integração de mensageria descreve possibilidade de entrega e assinatura, não uma nova publicação iniciada pelo Broker.
- Não permitir `Broker → Broker` nem `Cliente → Database`.
- Uma sessão WebSocket utiliza aresta dirigida para indicar iniciador; a mensagem bidirecional dentro dela não constitui automaticamente ciclo.
- Reaplicar regras existentes de duplicidade/estrutura/ciclos onde não houver substituição explícita. Topologias com entrega assíncrona não autorizam ciclos automáticos de publicação.

## 4. Regras particulares por perfil

### 4.1 Requisição/resposta

- REST e HTTP genérico: validar método/caminho no conjunto normativo futuro.
- SOAP: validar nome de operação e ação quando fornecida; não exigir processamento de XML real.
- GraphQL: aceitar somente Query/Mutation previstas nesta versão, com identificação da operação.
- gRPC unary: validar serviço e método; apenas uma requisição e uma resposta por chamada.
- CoAP: validar método, recurso e modo `CON`/`NON`; respeitar ACK piggybacked/separado sem obrigar ACK separado em todos os casos.
- Preservar configurações e tempo de processamento das APIs, separados de latência.

### 4.2 WebSocket

- Somente Cliente → API e API → API.
- Uma sessão virtual por conexão durante uma execução.
- Validar emissor de cada mensagem (origem ou destino), intervalos virtuais não negativos, quantidade finita, abertura e encerramento.
- Falha/timeout de abertura impede agendar mensagens de aplicação; falha terminal deve aparecer nos resultados.
- Mensagens independentes não exigem resposta anterior; empates de timestamp seguem ordenação determinística.

### 4.3 Broker e mensageria

- Identificar destino lógico e assinatura/consumidor elegível a partir de configuração e ligações consistentes.
- Queue: uma entrega por mensagem; múltiplos consumidores seguem round-robin determinístico.
- Topic: uma entrega por assinatura elegível.
- MQTT: QoS 0, correspondência exata do tópico; rejeitar QoS 1/2 e curingas nesta versão.
- Queue sem consumidor: mensagem aguardando até timeout virtual finito, terminalizada com resultado explícito.
- Topic/MQTT sem assinantes: publicação registrada com zero entregas (não inventar confirmação de consumo).
- Mensagens simuladas não geram loop de republicações infinitas.

## 5. Limites — valores a aprovar antes de implementar

Os contratos existentes de v2 documentam **máximos de 1.000 componentes, 3.000 conexões e 1.000.000.000 ms por propriedade de duração**. Esses números são **referências históricas do contrato existente**, não uma decisão de copiar os mesmos limites para todas as novas estruturas.

| Recurso | Direção aprovada | Valor final |
| --- | --- | --- |
| Componentes e conexões | Inicialmente reaproveitar limites existentes, sujeitos a validação técnica | **Pendente de ratificação** |
| Mensagens por sessão WebSocket | Teto finito | **Pendente** |
| Mensagens por simulação | Teto finito | **Pendente** |
| Assinaturas por tópico | Teto finito | **Pendente** |
| Eventos agendados/trace | Limite de segurança | **Pendente** |
| Duração virtual global | Limite de segurança | **Pendente** |
| Espera de Queue sem consumidor | Timeout virtual finito | **Pendente** |
| Profundidade de operações derivadas | Teto que impeça loops e explosão de eventos | **Pendente** |
| Tamanho de campos/payload lógico | Limites para proteção da API e memória | **Pendente** |

Nenhum valor numérico pendente será introduzido como aprovado no OpenAPI sem novo refinamento. As condições de timeout e limites devem terminar com resultado rastreável, não com finalização silenciosa.

## 6. Determinismo e conclusão

- Mesmo cenário e parâmetros produzem resultados ordenados equivalentes; eventos simultâneos têm desempate determinístico.
- Execução principal e conclusão global são independentes: publicação aceita encerra a principal, mas não as entregas derivadas.
- Sessão aberta e Queue aguardando consumidor impedem conclusão global até encerramento terminal.
- Resultados distinguem sucesso, falha, timeout e encerramento com pendências.
- Pausa, continuação, velocidade, passo a passo e reinício permanecem possíveis no playback.

## 7. Respostas e testes esperados

A API deve devolver violações identificáveis com caminho de campo e código estável; o status HTTP e schemas definitivos constarão do contrato normativo posterior.

Mínimos de teste: duplicidade de IDs, conexão inválida, tipo de integração incompatível, propriedades faltantes, intervalos negativos, WebSocket sem fechamento, assinatura inexistente, QoS inválido, Queue sem consumidor, Topic sem assinantes, múltiplos consumidores round-robin, mesmo timestamp e excesso de limite. Incluem-se regressões v0.1–v0.3.
