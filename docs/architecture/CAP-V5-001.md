# CAP-V5-001 — Capacidades, gatilhos e conexões dos componentes v0.5

> **Status:** especificação técnica proposta para revisão, não OpenAPI normativo e não implementação.  
> Base: [requisitos v0.5](../requirements/mvp-v0.5.md), [ADR-V5-001](ADR-V5-001.md), [v0.4.1](../requirements/mvp-v0.4.1.md).  
> Escopo: 15 componentes de serviço da v0.5; `SERVICE` substitui `API` como nó genérico, enquanto `Broker`, `Database` e tipos Client permanecem.

## 1. Princípios de design

1. Uma **conexão** determina o protocolo existente (`HTTP_REST`, `SOAP_HTTP`, `HTTP_GENERIC`, `GRAPHQL_HTTP`, `GRPC_UNARY`, `COAP`, `WEBSOCKET`, `QUEUE`, `TOPIC`, `MQTT`, `DATABASE_QUERY`). Não atribuir transporte a partir do ícone do componente.
2. O **tipo do componente** determina gatilhos aceitos, operadores nativos, propriedades específicas e limites de participação.
3. **Behavior/Actions** determinam os passos executados, explicitamente, sem percorrer automaticamente todas as arestas.
4. **Estado virtual tipado** pertence ao contexto de uma execução e usa o relógio único. Não criar banco, cache, provedor de mensagens ou motor de regras reais.
5. **Capacidades por função** são propostas, não Java enums/DTOs definitivos: reconciliar com as classes efetivamente disponíveis na branch de implementação.
6. Migrar explicitamente arquivos antigos com nó `API` para `SERVICE` sem perder IDs, relações, Behaviors/Actions nem semântica; preservar `Broker` e demais tipos existentes.

## 2. Capacidades compartilhadas propostas

| Código lógico | O que significa | Contrato mínimo |
| --- | --- | --- |
| `REQUEST_RECEIVER` | recebe request via aresta request/response compatível | operação, respondente, timeout/latência |
| `REQUEST_CALLER` | inicia chamada síncrona via CALL | aresta explícita e operação filha |
| `MESSAGE_PRODUCER` | publica em Broker | destino e conexão válidos |
| `MESSAGE_CONSUMER` | recebe delivery de Broker | subscription e mensagem correlacionada |
| `WEBSOCKET_PEER` | participante autorizado de sessão | sessão OPEN e direção válida |
| `SCHEDULED_SOURCE` | emite trigger virtual programado | quantia/horizonte finitos |
| `STATEFUL_RESOURCE` | conserva estado durante a execução virtual | chave, mutação e timestamp rastreáveis |
| `DECISION_PROVIDER` | produz decisão explícita para ações seguintes | resultado tipado e regra/condição finita |
| `ROUTER` | escolhe conexão dentre opções explicitamente configuradas | match, fallback/erro |
| `TRANSFORMER` | aplica transformação **descritiva** a payload virtual | entrada/saída rastreáveis e sem script livre |

As capacidades **não** substituem a matriz de conexões: uma origem capaz de CALL ainda precisa de aresta e integração adequadas.

## 3. Matriz preliminar de gatilhos e Actions

Legenda de gatilho: `REQ` = REQUEST_RECEIVED; `MSG` = MESSAGE_CONSUMED; `WS` = WS_MESSAGE_RECEIVED; `SESSION` = SESSION_OPENED; `SCHED` = SCHEDULED_TRIGGER (novo **proposto**).

Legenda de Actions atuais: `PROC` PROCESS, `CALL`, `PUB` PUBLISH, `RESP` RESPOND, `OPEN/WS_SEND/CLOSE`, `FORK/JOIN`.

| Componente | Gatilhos principais | Actions do núcleo e capacidades | Regra distintiva |
| --- | --- | --- | --- |
| Service | REQ/MSG/WS | PROC, CALL, PUB, RESP contextual, WS, FORK/JOIN | motor genérico; sem transporte próprio |
| API (apenas importação v0.4.1) | REQ/MSG/WS | Conversão explícita para SERVICE | Nenhum novo nó API; adaptar para Service na importação |
| API Gateway | REQ | PROC, CALL, RESP; ROUTER proposto | destino sempre escolhido por regra/Action |
| BFF | REQ | PROC, CALL, FORK/JOIN, RESP | composição e retorno para cliente |
| Worker | MSG, SCHED* | PROC, CALL, PUB, FORK/JOIN | não responde ao produtor em publicação |
| Scheduler | SCHED* ou entrada do cenário | SCHEDULE_TRIGGER* (proposta) | gera disparos finitos; sem job real |
| Authentication Service | REQ | PROC, RESP, EVALUATE_RULE* | autenticação fictícia; sem senha real |
| Webhook Receiver | REQ | PROC, CALL, PUB, RESP | recebe POST virtual, não cria listener externo |
| Orchestrator Service | REQ/MSG/SCHED* | PROC, CALL, PUB, FORK/JOIN, RESP contextual | coordena dependências, sem motor de workflow novo |
| Integration Bus / ESB | REQ/MSG | PROC, CALL, PUB, RESP contextual, TRANSFORM* | encaminha/transforma explicitamente; não substitui Broker |
| Cache | operação dedicada* | CACHE_GET/PUT/INVALIDATE* | estado por chave e TTL virtual |
| Object Storage | operação dedicada* | OBJECT_PUT/GET/DELETE* | identidade e tamanho/metadados de objeto |
| Notification Service | REQ/MSG | PROC, SEND_NOTIFICATION* | entrega lógica, nunca e-mail/SMS real |
| Search Engine | operação dedicada* | INDEX_DOCUMENT/SEARCH_DOCUMENTS* | índice virtual, busca determinística |
| Service Registry | operação dedicada* | REGISTER/UNREGISTER/DISCOVER* | lista de instâncias lógicas, sem DNS real |
| Rules Engine | operação dedicada* | EVALUATE_RULE* | devolve decisão tipada; branching depende de Action condicional futura |

O asterisco **`*` significa extensão candidata**, ainda não presente no OpenAPI 0.4.1. Não expor no frontend nem implementar antes de aprovar a semântica e o contrato. `RESP` sempre exige contexto com chamador de request.

## 4. Matriz de conexões — orientação por papel

| Origem | Destino | Perfil permitido (proposta) | Observações |
| --- | --- | --- | --- |
| Client | Gateway/BFF/Service/Webhook | request/response compatível | arquivos com API histórica são migrados para Service; nunca criar sessão WS automaticamente |
| Gateway/BFF/Service/Orchestrator | Service/Authentication/Rules | request/response compatível | CALL explícito, timeout local |
| Service/Worker/Orchestrator/ESB | Broker | QUEUE/TOPIC/MQTT | PUBLISH, nome de destination e aceitação |
| Broker | Worker/Service/ESB/Notification | QUEUE/TOPIC/MQTT conforme subscription | entrega causal, não novo publish automático |
| Service/Worker/BFF/Orchestrator | Cache/Object Storage/Search/Registry | perfil lógico de operação **a definir** | não forçar HTTP_REST em todos sem decisão |
| Client/Service | Notification Service | request/response compatível **ou** entrega por Broker | notificação é efeito virtual, não WS_SEND implícito |
| Service | Database | DATABASE_QUERY | manter validação DB existente |
| Client/Service | participante WS compatível | WEBSOCKET | OPEN explícito, mensagens com sessão OPEN |

**Ponto aberto importante:** os recursos Cache/Storage/Search/Registry têm operações tipadas, mas a v0.4.1 possui conexões orientadas a `integration.kind`. Antes da implementação, escolher uma das alternativas: (A) perfil lógico `RESOURCE_OPERATION` novo, (B) reutilizar `HTTP_REST` com semântica de operação em Action, ou (C) definir Action de recurso com `connectionId` e exigir um `integration.kind` existente compatível. **Não inventar perfil de rede em silêncio**. Qualquer solução precisa de schema OpenAPI, matriz e teste de regressão.

## 5. Entradas e saídas por tipo

- **Gateway:** matcher de rota/operação; destinos ordenados e fallback definido; resposta do destino preservada ou transformada **apenas se configurada**.
- **BFF:** compõe resultados de dependências declaradas; falhas de uma chamada não são ignoradas; `JOIN` tem política explícita de conclusão.
- **Worker:** inicia processamento a partir do delivery; registra `messageId` e `deliveryId`; falha contribui para `globalStatus`, não altera response principal concluído.
- **Scheduler:** quantidade `1..N`, instantes `t>=0` ordenados, orçamento total e duração finita; evento de disparo identifica `scheduleId`, `occurrenceIndex` e `rootOperationId`. Definir se múltiplos disparos são filhos de uma operação principal antes do OpenAPI.
- **Authentication Service:** entrada com metadados *fictícios*, resultado `AUTHORIZED|DENIED|ERROR`; nunca armazenar credenciais, gerar JWT válido ou fazer integração real.
- **Webhook Receiver:** recebe HTTP virtual; devolve resposta conforme Actions sem esperar async downstream por padrão.
- **Orchestrator:** descreve dependências explícitas entre operações; não consome toda aresta conectada.
- **ESB:** recebimento → TRANSFORM virtual configurada → encaminhamento; publish/delivery requer Broker.
- **Notification:** canal `EMAIL|SMS|PUSH` lógico, destino fictício, status `SENT|FAILED`; sem provedor real.

## 6. Validação e códigos propostos

| Código proposto | Condição |
| --- | --- |
| `INVALID_COMPONENT_CAPABILITY` | gatilho/Action incompatível com papel |
| `INVALID_RESOURCE_CONNECTION` | aresta/recurso/operação sem compatibilidade |
| `INVALID_ROUTING_RULE` | rota ambígua, destino inexistente ou sem fallback |
| `INVALID_SCHEDULE` | eventos não finitos, fora do horizonte ou sem entrada causal |
| `INVALID_VIRTUAL_RESOURCE_OPERATION` | ação sem chave/objeto/índice/recurso |
| `INVALID_DECISION_RULE` | regra de decisão ausente/contraditória/ambígua |
| `UNRESOLVED_SERVICE` | descoberta sem instância elegível em runtime |
| `VIRTUAL_RESOURCE_NOT_FOUND` | recurso não existente em operação virtual |
| `VIRTUAL_RESOURCE_EXPIRED` | valor de Cache expirou no clock virtual |

Erros de **configuração** aparecem no validador da arquitetura/cenário (violation). Falhas **dinâmicas** aparecem no trace e na resposta da simulação, sem serem transformadas automaticamente em HTTP 500.

## 7. Limites e compatibilidade

- Estados virtuais somente dentro de uma execução, salvo decisão futura explícita de persistência.
- Cada operação tem ID/correlation e timestamp; relógio e fila únicos.
- Iterações, loops, notificações, índices e entradas de cache respeitam budgets finitos.
- Não implementar retries, backoff, circuit breaker, balanceamento real, rede real nem credenciais.
- Preservar Database, Broker, tipos Client e `UnifiedScenario`; converter explicitamente nós API antigos em Service via adaptador legado.
- `Load Balancer` e `CDN` permanecem fora da v0.5 (infraestrutura futura).

## 8. Gate para etapa seguinte

Para elaborar o OpenAPI normativo, decidir: (1) modelo dos recursos lógicos; (2) novos kinds de Action e dados de retorno; (3) trigger agendado; (4) decisão/branch; (5) regras de fallback e timeout. O catálogo está aprovado, **mas essas interfaces são propostas para revisão**.
