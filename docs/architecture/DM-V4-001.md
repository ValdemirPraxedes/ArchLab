# DM-V4-001 — Modelo de domínio e execução da v0.4

> **Status:** diretrizes de modelagem aprovadas em 2026-11-04; detalhes de classes Java e DTOs ainda não normativos. Documento de planejamento, sem autorização de implementação.
>
> Referências: [requisitos](../requirements/mvp-v0.4.md), [ADRs](ADR-v0.4.md), [contrato preliminar da API v1](../api/API-V4-001.md), [validações](VAL-V4-001.md).

## 1. Objetivo e invariantes

Evoluir o domínio já existente sem substituir o motor determinístico, o grafo de arquitetura, o transporte virtual ou a experiência do editor. Suportar os dez perfis aprovados, os seis tipos de cliente v0.3, API, Database e o novo Broker genérico. **Não executar protocolos reais.** Continuar com uma única operação principal por execução e permitir operações derivadas finitas.

A separação entre componentes, conexões, integrações, cenários, estado virtual e resultados é conceitual. Os nomes de tipos a seguir são **modelos lógicos propostos**, não instruções para criar uma hierarquia de classes ou um novo motor.

## 2. Estruturas lógicas de arquitetura

| Modelo | Campos ou responsabilidades | Invariantes |
| --- | --- | --- |
| `Architecture` | `components[]`, `connections[]` | IDs únicos, referências válidas, estrutura validável |
| `Component` | `id`, `type`, `displayName`, propriedades específicas | Preservar identidade do componente até a saída da simulação |
| `Connection` | `id`, `sourceId`, `targetId`, `latencyMs`, `integration` | Aresta dirigida; perfil compatível com tipos de ponta |
| `Integration` | `kind` e atributos específicos do perfil | União discriminada; sem campos irrelevantes de outros perfis |
| `ExecutionScenario` | Operação inicial, identificador da origem, conexão de entrada, parâmetros semânticos | Uma operação principal; configurações compatíveis com perfil |

### 2.1 Tipos de componentes

- Clientes: `WEB_BROWSER`, `MOBILE_APP`, `DESKTOP_APP`, `CLI`, `BOT`, `EMBEDDED_SYSTEM`.
- `CLIENT` legado permanece interpretável para fins de migração.
- `API` permanece capaz de processar requisições, chamar APIs e atuar como produtor/consumidor de mensagens dentro das topologias aprovadas.
- `DATABASE` preserva integração existente via API.
- `BROKER` é **o único novo componente**: seus destinos lógicos não são nós adicionais no canvas.

Os seis clientes podem ser tratados por capacidades/semântica comum, sem herança de classes obrigatória. A API v1 consolidada reconhecerá os seis tipos sem exigir conversão para `CLIENT` no contrato canônico; adaptadores temporários podem continuar necessários para clientes legados.

### 2.2 Broker, destinos e inscrições

| Estrutura lógica | Propriedades/responsabilidades |
| --- | --- |
| `Broker` | Identidade, destinos lógicos e estado virtual da execução |
| `BrokerDestination` | Nome, tipo lógico (fila ou tópico) e configuração permitida |
| `BrokerSubscription` | Destino lógico, API consumidora elegível e conexão `Broker → API` |
| `BrokerMessage` | Identidade, operação causal, destino lógico, perfil e estado |
| `BrokerDelivery` | Identidade própria, mensagem de origem, consumidor/assinatura, agendamento e resultado |

A configuração de fila/tópico/assinatura deve ser consistente com as conexões reais no grafo, sem dupla fonte de verdade. Queue escolhe um consumidor elegível por mensagem, por round-robin determinístico; Topic e MQTT produzem uma entrega lógica por inscrição elegível; MQTT limita-se a QoS 0 e tópicos exatos. **Não implicar garantias reais de entrega.**

## 3. Integrações semânticas

| Família | Perfis |
| --- | --- |
| Requisição/resposta | REST, SOAP, HTTP genérico, GraphQL HTTP, gRPC unary, CoAP |
| Sessão bidirecional | WebSocket |
| Mensageria por Broker | MQTT, Queue Messaging, Topic Messaging |
| Compatibilidade anterior | Integração API → Database já existente (não conta como perfil v0.4) |

`Integration.kind` identifica a variante. A lista canônica e os campos requeridos serão fixados em [API-V4-002](../api/API-V4-002.md), após aprovação. Não copiar indiscriminadamente payloads HTTP para MQTT ou WebSocket. Latência pertence à conexão, processamento ao componente.

## 4. Cenário e plano de execução

Distinguir três **modalidades lógicas** da operação inicial:

1. `REQUEST_RESPONSE`: chamada que produz resposta, incluindo cadeias API → API e API → Database quando válidas.
2. `WEBSOCKET_SESSION`: abertura de sessão em Cliente → API ou API → API, com sequência finita de mensagens nos dois sentidos e encerramento.
3. `MESSAGE_PUBLISH`: publicação/envio lógico ao Broker via Queue, Topic ou MQTT.

Preservar `entryComponentId` e `entryConnectionId` onde couber. A escolha do campo discriminador, estruturas de payload e validação de dependências serão fechadas no contrato normativo. Uma sessão bidirecional **não é, por si só, ciclo estrutural**.

## 5. Estado virtual independente

O contexto de cada execução deve manter informações **independentes e correlacionáveis** de:

- Requisições e respostas, com estado próprio.
- Sessões WebSocket, com abertura, mensagens, fechamento e término por erro/timeout.
- Mensagens de Broker e entregas individuais, inclusive pendências.
- Recursos ativos e operações derivadas ainda não terminadas.
- Execução principal e conclusão global, com status e resultado separados.

Reutilizar identificadores e máquinas de estado existentes sempre que suficientes. Estados ilustrativos:
- Requisição: `CREATED → SENT → PROCESSING → COMPLETED`.
- Sessão: `CONNECTING → OPEN → CLOSING → CLOSED`.
- Mensagem: `CREATED → ACCEPTED → QUEUED/ROUTED → DELIVERED → PROCESSED` (somente estágios aplicáveis).

Falha, timeout e encerramento com pendências exigem resultados terminais explícitos. **Conclusão principal não encerra automaticamente entregas derivadas**, e sessão ainda aberta bloqueia a conclusão global.

## 6. Agendador, transporte e correlação

Manter relógio virtual e agendador determinístico únicos. O transporte valida ligações, aplica latência e agenda transporte lógico. O comportamento da integração/participante decide se a operação é uma resposta, uma mensagem de sessão ou uma publicação com destinatários múltiplos.

Os eventos precisam permitir correlação lógica entre execução, operação principal, operação derivada, componente, conexão, sessão e perfil quando aplicável. Os campos `executionId`, `eventId`, `operationId`, `parentOperationId`, `componentId`, `connectionId`, `sessionId`, `timestamp`, `eventType` e `status` são **conceituais**, não DTOs definitivamente aprovados.

## 7. Representação e resultados

Preservar grupos atuais `execution`, `initialState`, `trace`, `timeline`, `metrics` e `messageRepresentations`; estender de forma rastreável e compatível quando possível. A resposta deve diferenciar conclusão da operação principal, conclusão global e os resultados (sucesso, falha, timeout, pendência terminalizada).

O frontend apenas reproduz e apresenta os resultados; não toma decisões do motor.

## 8. Compatibilidade, exclusões e pendências

- Consolidar API pública exclusivamente sob `/api/v1` e migrar/retirar `/api/v2` conforme ADR-V4-006, sem eliminar funcionalidades internas.
- Preservar cenários e controles v0.1–v0.3.
- Não implementar rede real, Broker externo, persistência de mensagens, QoS 1/2, retries, DLQ, múltiplas sessões WebSocket por conexão ou loops ilimitados.
- **Pendentes:** estrutura Java real, discriminação normativa de cenários, propriedades detalhadas de Broker, nomes finais de enums, status e eventos, limites numéricos e contratos OpenAPI. Não pressupor que este documento já é um schema validado.

## 9. Critério de aceitação do modelo

Os modelos devem suportar sem conversões silenciosas: um cliente específico chamando API, duas APIs com WebSocket bidirecional, Queue com um consumidor, Topic com duas assinaturas, MQTT QoS 0, mensagem sem consumidor, timeout e conclusão global depois da última derivada. Tudo reproduzível sob o relógio virtual.
