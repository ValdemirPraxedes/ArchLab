Este documento consolida a decisão mais recente de reduzir a v0.3 a uma entrega visual/estrutural pequena. **Prevalece para o escopo da v0.3** sobre as ideias mais amplas registradas anteriormente em [mvp-v0.3.md](mvp-v0.3.md), [v0.3-clients.md](v0.3-clients.md) e [v0.3-services.md](v0.3-services.md). Essas discussões permanecem como histórico e backlog para versões futuras.

## 1. Objetivo

Disponibilizar seis tipos distintos de clientes no editor visual do ArchLab, com operações básicas de edição, identificação e representação no modelo da arquitetura. Organizar a paleta lateral por categorias, preservando a experiência de uso do editor atual.

**Tipos selecionados:** Web Browser, Mobile App, Desktop App, CLI, Bot e Embedded System.

**Definição de Cliente no ArchLab:** componente de software que interage com o ambiente externo por interfaces físicas ou digitais, podendo receber estímulos humanos, ambientais ou automatizados e iniciar comunicações com outros componentes. Nesta entrega, essa definição orienta a classificação **sem implementar** as comunicações ou o disparo de estímulos.

## 2. Requisitos funcionais

| ID | Requisito | Critério de aceitação |
| --- | --- | --- |
| **RF-01** | **Disponibilizar seis tipos de clientes na paleta.** | Web Browser, Mobile App, Desktop App, CLI, Bot e Embedded System aparecem individualmente na paleta do editor. |
| **RF-02** | **Adicionar clientes ao canvas.** | O usuário consegue adicionar uma instância de cada um dos seis tipos ao canvas usando a interação existente. |
| **RF-03** | **Selecionar e movimentar clientes.** | Clientes adicionados podem ser selecionados e movidos sem perder identificação e posição. |
| **RF-04** | **Editar o nome do cliente.** | O nome pode ser alterado no painel de propriedades e a alteração aparece no editor. |
| **RF-05** | **Remover clientes.** | É possível remover uma instância de cliente sem afetar indevidamente outros componentes. |
| **RF-06** | **Identificação visual específica por tipo.** | Cada um dos seis clientes tem nome e ícone próprios; os ícones são distinguíveis. |
| **RF-07** | **Representar tipo e propriedades no modelo da arquitetura.** | O estado/modelo do editor mantém o tipo específico, nome e posição de cada instância durante as operações de edição. Não implica implementar persistência em banco ou salvamento de projetos. |
| **RF-08** | **Agrupar a paleta por categorias.** | A paleta apresenta títulos de categoria e agrupa os componentes conforme a tabela da seção 3; todos continuam podendo ser adicionados ao canvas. |

## 3. RF-08 — Categorias da paleta

| Categoria | Componentes mostrados |
| --- | --- |
| **Clientes** | Web Browser, Mobile App, Desktop App, CLI, Bot, Embedded System |
| **Serviços** | API (componente existente) |
| **Dados** | Database (componente existente) |

**Critérios adicionais do RF-08:**
- Os títulos de categoria precisam ser visualmente identificáveis.
- Preservar nome e ícone de cada componente.
- O agrupamento não pode prejudicar o arrastar/adicionar componentes nem alterar desnecessariamente o layout do editor.
- A organização deve comportar novas categorias posteriormente, sem reestruturar toda a paleta.
- **Categorias expansíveis/recolhíveis não são requisito desta versão**; são somente possibilidade visual futura.

## 4. Requisitos de qualidade e limites

- **RQ-01 — Simplicidade:** mudanças estritamente necessárias nos dados de componentes e na paleta; sem redesenho do canvas, propriedades ou controles.
- **RQ-02 — Estabilidade do editor:** adicionar, selecionar, mover, editar e remover componentes existentes deve continuar funcionando.
- **RQ-03 — Coerência visual:** usar o padrão visual e a biblioteca de ícones já adotados no ArchLab, evitando novos padrões paralelos.
- **RQ-04 — Tipagem:** o modelo da arquitetura deve distinguir os seis tipos de cliente sem ambiguidades.
- **RQ-05 — Estado não executável:** o editor/simulador não deve apresentar os seis clientes novos como plenamente simuláveis nesta entrega. Se um cenário contiver apenas clientes ainda sem suporte de execução, a execução deve ser impedida com mensagem clara, sem simulação fictícia.

## 5. Explicitamente fora da v0.3

- **Nenhuma conexão dos seis novos clientes** com API, Service, Database ou outro componente.
- **Nenhuma simulação dos seis novos clientes**, geração de requisições ou eventos para eles.
- Nenhum dos dez perfis discutidos será implementado nesta entrega: REST (HTTP), SOAP (HTTP), GraphQL (HTTP), WebSocket, gRPC, MQTT, CoAP, HTTP genérico, Queue Messaging ou Topic Messaging.
- Não incluir novos Services, API Gateway, BFF, Worker, Scheduler, Authentication Service, Webhook Receiver, Orchestrator Service, Broker ou Integration Bus / ESB.
- Não implementar disparos automáticos de Bot, sensores ambientais de Embedded System, novas regras de rede, persistência de projetos, workflow, Undo/Redo ou ferramentas extras.
- Não exigir retrocompatibilidade entre todas as versões 0.x; porém não quebrar comportamentos existentes sem uma necessidade concreta desta entrega.

## 6. Roteiro de validação manual

Para cada um dos seis tipos, o responsável pela validação deverá:

1. Encontrar o componente na categoria **Clientes**.
2. Adicioná-lo ao canvas.
3. Selecioná-lo e deslocá-lo.
4. Alterar seu nome e verificar a identificação visual.
5. Confirmar que o tipo correto permanece no modelo do editor.
6. Removê-lo.
7. Verificar que os componentes já existentes (API e Database) continuam acessíveis em suas categorias e que o editor segue operável.

**Resultado esperado:** os seis clientes são utilizáveis como elementos de modelagem visual. **Não faz parte da validação acionar uma simulação com esses novos clientes nem conectá-los a uma API.**

## 7. Entregas pequenas sugeridas

1. Atualizar tipagem/modelo e paleta por categoria (**RF-01, RF-07, RF-08**).
2. Adicionar os seis tipos com ícones específicos (**RF-02, RF-06**).
3. Verificar edição e movimentação dos seis tipos (**RF-03, RF-04, RF-05**).
4. Realizar testes e validação manual dos cenários acima.

Essa divisão é orientação de planejamento; os cards de desenvolvimento e a priorização final serão refinados separadamente.

## 8. Backlog futuro preservado

As discussões sobre dez perfis de comunicação, Service, timeout, API Gateway, mensageria IBM MQ/TIBCO EMS, Broker e Integration Bus permanecem registradas para próximas versões. **A seleção conceitual dessas tecnologias não amplia o escopo desta v0.3.**
