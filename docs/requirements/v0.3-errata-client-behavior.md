# ArchLab v0.3 — Errata 01: comportamento funcional dos seis clientes

- **Data:** 2026-11-03
- **Status:** decisão de produto aprovada; implementação corretiva pendente
- **Origem:** refinamento posterior à execução das tarefas FE-01 a FE-06
- **Documentos afetados:** [requisitos v0.3](v0.3-client-requirements.md) e [ADR v0.3](../architecture/ADR-v0.3.md)
- **Regra de precedência:** esta errata substitui explicitamente os trechos conflitantes desses documentos. Os demais RFs permanecem válidos.
- **Histórico:** manter os documentos e commits originais como registro das decisões da fase anterior.

## 1. Motivo

Na entrega inicial, os seis tipos de clientes foram definidos somente para modelagem visual, sem conexão ou simulação. Após a execução das seis tarefas, identificou-se que o comportamento funcional do componente `CLIENT` existente pode ser **reutilizado**, sem implementar seis motores distintos.

A intenção é que os seis clientes representem papéis diferentes **visualmente e no modelo do editor**, mas compartilhem o **mesmo comportamento de requisição/resposta do CLIENT atual** nesta versão.

## 2. Decisões corretivas

1. **Remover o componente `Client` genérico da paleta de componentes**, substituído pelos seis tipos: Web Browser, Mobile App, Desktop App, CLI, Bot e Embedded System.
2. **Manter internamente o suporte ao tipo `CLIENT` legado**, quando necessário para interpretar cenários e manter o motor v2. Não exibir o tipo genérico como opção de criação na paleta.
3. **Permitir conexões dos seis clientes com API** utilizando **apenas os protocolos já suportados** pelo fluxo atual de `CLIENT → API` (atualmente REST e SOAP). Não ampliar os dez perfis debatidos.
4. **Executar simulações dos seis clientes com comportamento funcional idêntico ao `CLIENT`**, incluindo ciclo de envio, processamento, resposta, estados, timeline e resultados conforme suportado pela v0.2.
5. **Preservar a identidade do tipo no frontend** e adaptar os novos tipos para `CLIENT` **somente na fronteira de serialização da API v2**. Preservar ID, nome, conectividade e propriedades relevantes no payload. Não reescrever o estado do editor para `CLIENT`.
6. **Reutilizar validação de conexão e regras de cenário existentes** para os seis tipos; não liberar ligações arbitrárias com Database nem alterar a semântica do motor.
7. **Manter backend inalterado** se a adaptação no frontend atender os requisitos sem quebrar o contrato v2. Qualquer necessidade de mudança no backend deve ser justificada e submetida para avaliação antes de ampliar o escopo.
8. **Conservar a paleta categorizada** conforme RF-08: Clientes (seis tipos), Serviços (API), Dados (Database).

## 3. Alterações de requisitos

| Requisito | Ajuste |
| --- | --- |
| RF-01 | A categoria Clientes exibe **somente os seis tipos específicos**, não o Client genérico. |
| RF-07 | O tipo específico permanece no estado local; na API v2 é mapeado para o tipo funcional CLIENT apenas na camada adaptadora. |
| RF-08 | Mesmas três categorias e componentes já aprovados; o Client genérico não aparece na paleta. |
| RQ-05 | **Substituído:** em vez de bloquear conexões/simulações dos seis clientes, integrar os seis ao comportamento Client atual, com validação compatível e sem suportar os demais perfis. |
| **RF-09 (novo)** | Permitir criar conexão de cada um dos seis clientes para API via protocolo já suportado pelo CLIENT (REST/SOAP). |
| **RF-10 (novo)** | Permitir simular cada um dos seis clientes pela API v2, recebendo e exibindo resultado equivalente ao Client genérico atual. |
| **RF-11 (novo)** | Não exibir Client genérico na paleta; preservar seu suporte interno enquanto for necessário. |

### Critérios de aceitação adicionais

- Um usuário pode montar `Web Browser → API` com REST, executar e ver eventos/timeline/resultado; o mesmo vale para cada um dos outros cinco tipos (com protocolos atualmente aceitos).
- Simulações com `Cliente específico → API → Database` reutilizam os mesmos comportamentos e métricas da versão v0.2.
- Ao clicar em Simular, os nós no canvas **continuam exibindo seus tipos específicos**.
- As conexões incompatíveis continuam rejeitadas e não há novos perfis nesta entrega.
- O payload enviado ao backend v2 usa tipos aceitos pelo contrato (`CLIENT`, `API`, `DATABASE`); não duplica nós e preserva IDs das relações.
- Cenários existentes continuam funcionando; drag-and-drop, edição, nomes, ícones e categorias não sofrem regressão.

## 4. Itens fora do escopo

- Comportamentos distintos por tipo de cliente (navegador real, SDK mobile, CLI real, automação Bot, sensor físico).
- MQTT, GraphQL, gRPC, WebSocket, CoAP, Queue, Topic e outros perfis não suportados no fluxo atual; **nenhuma implementação nova dos dez perfis**.
- Novos componentes ou mudanças na engine Java, salvo descoberta fundamentada e aprovada separadamente.

## 5. Plano de correção pós FE-01–FE-06

- **FE-07:** ocultar `Client` genérico da paleta, preservando suporte interno.
- **FE-08:** habilitar compatibilidade e conexões de cada novo cliente para API usando o mecanismo atual.
- **FE-09:** adaptar serialização à API v2, cenário e validação para executar todos os tipos com comportamento CLIENT.
- **FE-10:** cobrir os seis fluxos com testes automatizados, regressão e validação manual de ponta a ponta.
- **FE-11:** atualizar a defesa técnica/diagramas do desenvolvedor e registrar a mudança como correção do escopo após execução inicial.

**Processo:** executar em branch de implementação específica, commits por tarefa, um PR final com defesa técnica; sem merge automático e sujeito à avaliação do responsável.
